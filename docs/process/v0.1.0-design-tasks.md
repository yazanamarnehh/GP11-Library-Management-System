# v0.1.0-design — Task briefs per team member

The `v0.1.0-design` checkpoint is split so that **each member owns and commits one part** on their
own branch. Each brief is written so a member can open the repo in Claude Code and say:

> Do **Task X** from `docs/process/v0.1.0-design-tasks.md`.

Claude in this repo will create the prompt record, the AI-log row and the branch as required by
`CLAUDE.md`.

## Order and dependencies

1. **Task A** (requirements and plan) is merged into `dev` first — the others reference its IDs and glossary.
2. **Tasks B, C and D** then run in parallel, each on its own branch from the updated `dev`.
3. When A–D are merged, tag `v0.1.0-design` on the merged `dev` commit.

Every PR needs **one approval from another member** (repository ruleset). Review each other's work —
the reviewer's name goes in the *Student Review* column of `docs/ai_development_log.md`.

## Shared conventions (all tasks)

- Diagram tool: **PlantUML**, sources in `uml/*.puml`, PNG exports in `uml/rendered/<same-name>.png`.
  Render with the IntelliJ "PlantUML Integration" plugin, the VS Code PlantUML extension, or `plantuml.jar`.
- Use **exactly** the class, status and actor names from the glossary in
  [project_description.md](../project_description.md#6-glossary-shared-vocabulary--use-these-exact-names-in-uml-and-code).
- Reference requirement IDs (FR/NFR/BR) in diagram notes or in the accompanying doc text.
- Decided architecture (see [architecture.md](../architecture.md) §5–6): one Spring Boot application
  with Thymeleaf UI, PostgreSQL database, layered and package-by-feature
  (`catalog`, `member`, `security`, `circulation`, `reservation`, `fine`, `notification`, `report`),
  run with Docker Compose. Email and payments are simulated.
- When a diagram is added, list it in the README *Architecture and diagrams* table and update the
  *Use Case / Design Element* column of `docs/traceability_matrix.md` if needed.

## Task C — Use cases and catalog sequence diagrams  *(owner: TBD)*

**Branch:** `docs/v0.1.0-use-cases`

**Produce**
1. `uml/use-case.puml` — use case diagram for the **whole system**: actors Guest, Member, Librarian,
   Administrator, Scheduler; one use case per FR group (name use cases as in the *Use Case* column of
   `docs/traceability_matrix.md`, e.g. "Search catalog", "Check out copy"). Use `<<include>>` where
   a use case always reuses another (e.g. Check out copy includes Verify member eligibility) and
   generalisation Guest ← Member.
2. `docs/use_cases.md` — fully dressed descriptions for the **important** use cases:
   Search catalog, Manage titles, Manage copies, Check out copy, Return copy, Renew loan,
   Reserve title, Record fine payment. Template per use case: ID, name, actors, related FR/BR,
   preconditions, main success scenario (numbered), alternative/exception flows, postconditions.
3. `uml/seq-catalog-search.puml` — sequence: Guest → `CatalogController` → `CatalogService` →
   `TitleRepository` → PostgreSQL, returning results with available-copy counts (FR-05, NFR-02).
4. `uml/seq-catalog-add-copy.puml` — sequence: Librarian adds a copy to a title, including the
   duplicate-barcode exception path (FR-03).

**Acceptance criteria**
- Every FR-01–FR-34 maps to at least one use case (add a coverage table at the end of `use_cases.md`).
- Sequence diagrams use the class names that Task D uses in the class diagram.
- PNGs committed to `uml/rendered/`.

## Task D — Domain model: class diagram, ERD, copy state diagram  *(owner: TBD)*

**Branch:** `docs/v0.1.0-domain-model`

**Produce**
1. `uml/class-domain.puml` — domain class diagram for the **whole system**: `Title`, `Author`,
   `Category`, `BookCopy`, `Member`, `UserAccount`, `Role` (enum), `Loan`, `Reservation`, `Fine`,
   `Payment`, `Notification`, `LendingPolicy` (BR values) and the status enums from the glossary.
   Show key attributes (with types), important operations (e.g. `Loan.isOverdue()`,
   `Loan.renew(policy)`, `Fine.outstanding()`), associations with multiplicities
   (e.g. Title 1 — 0..* BookCopy, Title * — 1..* Author), composition where lifecycles are bound.
2. `uml/erd.puml` — ERD (PlantUML entity syntax) for the same model: tables, primary/foreign keys,
   unique constraints (ISBN, barcode, member number, email) and the constraint that a copy has at most
   one active loan (NFR-03). Include audit columns required by NFR-09.
3. `uml/state-book-copy.puml` — state diagram for `BookCopy`: `AVAILABLE`, `ON_LOAN`, `ON_HOLD`,
   `LOST`, `DAMAGED`, `WITHDRAWN`, with transitions labelled by the triggering action and FR
   (e.g. *checkout [FR-13]*, *return, reservation waiting [FR-23]*). Must match FR-04's restrictions.
4. A short `docs/domain_model.md` explaining each class and the key design choices.

**Acceptance criteria**
- Names exactly match the glossary; enums match the status lists.
- Every multiplicity is justified by a requirement or business rule (note it in `domain_model.md`).
- ERD and class diagram are consistent (same entities, same relationships).
- PNGs committed to `uml/rendered/`.
